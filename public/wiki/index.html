RADARSite.

RADARSite is the web platform for RADARCharts by REM. This repository contains the application code and supporting tools used to develop, test, and maintain the site.

This Wiki is the project handbook for developers, maintainers, and AI agents working on RADARSite. It explains how the project is organized, how to work on it safely, and where to find the relevant technical guidance.

(03)

What this repository contains

Directory map

  • src/app/Next.js application routes and route-level behavior.
  • src/components/shared interface components.
  • src/lib/application utilities and supporting logic.
  • scripts/development, validation, diagnostics, and maintenance scripts.
  • cloudflare/Cloudflare-related project files.
  • docs/project documentation.
  • reports/reports and audit-related material.
  • qa-artifacts/quality-assurance artifacts.

The repository also contains tests and validation scripts for areas such as end-to-end behavior, accessibility, Content Security Policy, CMS contracts and diagnostics, media migration, and live-route checks. Consult the relevant script and its current instructions before running it.

(04)

Run the application locally

Local setup

The repository README documents this basic setup:

ShellInstall & configure
$ npm install
$ cp .env.local.example .env.local

Add the required values to .env.local, then start the development server:

ShellDev server
$ npm run dev

Use Node.js 20 or newer. Check the README and environment example for the current required variables and any setup changes. Do not copy credentials into the Wiki, commit them, or paste them into prompts or issue reports.

(05)

Common project commands

package.json

The repository includes scripts for tasks such as:

  • npm run buildbuild the application.
  • npm run startstart the production server.
  • npm run lintrun lint checks.
  • npm run typecheckrun TypeScript checks.
  • npm run testrun the configured test suite.

Additional Playwright, accessibility, security, CMS, migration, and route-verification scripts are available. Check package.json before running a command; the script names, prerequisites, and expected environment may change.

Note

A successful build is not, by itself, proof that production data access, external services, or every live route is working. The project documentation notes that production builds intentionally avoid database access and that database behavior is checked through contract-test scripts.

(06)

How we work on RADARSite

Working principles

  1. 01
    Inspect before changing.

    Read the relevant code, configuration, documentation, and existing tests first.

  2. 02
    Keep the change scoped.

    Avoid unrelated refactors, dependency changes, or design changes.

  3. 03
    Verify the affected behavior.

    Run the relevant checks and report exactly what passed, failed, or could not be run.

  4. 04
    Separate preparation from execution.

    Treat production deployments, DNS changes, environment-variable changes, database changes, and data migrations as consequential operations that require an explicit plan and authorization.

  5. 05
    Report evidence, not assumptions.

    Distinguish verified results from inferred behavior, planned work, and blocked checks.

(07)

Working with AI coding agents

Agent protocol

AI agents should read the relevant Wiki page and repository instructions before making changes. They must not assume that a documented integration is connected, that a deployment is current, or that a script is safe to run against production.

For every task, report:

  • the files and behavior examined;
  • the proposed or completed changes;
  • the checks actually executed and their results;
  • any unverified assumptions, blockers, or required human approval.
Never include

Do not include secrets, access tokens, private credentials, or sensitive production data in prompts, commits, Wiki pages, or reports.

(08)

Documentation maintenance

Keeping it true

Keep this Home page short and dependable. Put detailed procedures in their own pages and link to them here.

When documentation changes:

  • verify instructions against the current repository;
  • identify whether a statement describes current, planned, or historical behavior;
  • remove or correct obsolete instructions;
  • avoid duplicating large sections of the README or source documentation;
  • update links when pages are renamed.

Historical audit and migration reports may be useful evidence, but they should not be treated as current operating instructions without verification.
