Architecture.

How a request becomes a page: the route tree, the content read model, the media and storage adapters, the Studio write path, and the concerns that apply to every route.

This page describes the structure of the application as it exists in the repository. It is a map of the code, not a statement about which environment is deployed or which integration is currently connected.

Framework
Next.js 16 · App Router
Language
TypeScript
Styling
Tailwind CSS v4
Runtime
Node.js 20+ · Workers
Read this as a map, not a guarantee

Every statement below is traceable to a file in the repository. Where the code selects behaviour from an environment variable, this page names the variable rather than asserting which value is set in production. Confirm the live configuration before relying on any path described here for an operational change.

(01)

Request lifecycle

From URL to HTML

RADARSite is a Next.js App Router application. A page is a React Server Component by default: it runs on the server, reads content, and streams HTML. Only components marked "use client" — the header, the theme toggle, motion providers, the Studio panels — ship JavaScript to the browser.

The sequence below is the path a public page request takes. Steps 3 and 4 differ by route group; the rest are shared.

  1. 01
    The request reaches the runtime

    Either the Node server (next start) or the Cloudflare Worker built through vinext. The Worker entrypoint is declared in cloudflare.config.ts.

  2. 02
    Security headers are applied

    next.config.ts attaches the Content-Security-Policy and the companion headers to every response through a single /(.*) rule.

  3. 03
    The route group layout mounts

    A marketing route mounts the cursor and smooth-scroll providers around MarketingLayoutShell. A platform route mounts AppShell instead and is marked noindex.

  4. 04
    The page component reads content

    The page calls the content layer in src/lib/content-server.ts, which resolves the collections from the first available source in its fallback chain.

  5. 05
    HTML streams, then client components hydrate

    Server-rendered markup is sent first. Interactive islands — navigation, theme toggle, players, Studio — hydrate afterwards.

  6. 06
    Errors and events are reported

    Sentry captures server, edge and client errors; PostHog and Google Analytics record product events. Both are configured from environment variables and are inert when those variables are absent.

(02)

Route groups and the app tree

src/app/

src/app/ holds 46 page routes and 16 API route handlers. Route groups — directories in parentheses — do not appear in the URL; they exist to give a set of routes a shared layout.

Top-level areas of the app tree
Path Role
src/app/(marketing)/ The public site. Mounts CursorProvider, SmoothScrollProvider and MarketingLayoutShell — chrome, main#main-content, SiteFooter, playlist floater.
src/app/(platform)/ The signed-in application. The group layout sets robots: noindex, nofollow, noarchive, nosnippet; the (app) subgroup adds BriefsProvider and AppShell.
src/app/[...cmsPath]/ Catch-all for CMS-authored pages and release links. Resolves a path against readPublishedContent() and returns notFound() when nothing matches.
src/app/admin/ The Studio — the editorial write surface. Password-gated, not indexed.
src/app/api/ 16 route handlers: Studio operations, Notion publishing, media migration, release links, Spotify playlists, contact, cache maintenance.
src/app/omolops/, privacy/, terms/ Standalone routes outside both groups.

Rendering is chosen per route, not globally. Most editorial routes declare revalidate = 3600; the homepage declares dynamic = "force-dynamic" so a newly published story appears immediately; the press and spotlight archives combine force-dynamic with dynamicParams. Read the route file before assuming a page is static or dynamic.

(03)

The content layer

src/lib/content-server.ts

Content is not read from one place. readContentUncached() walks a fallback chain and returns the first source that answers. This is the single most important behaviour to understand before changing anything that reads content.

Read order — first match wins
Source Selected when Notes
Committed snapshot NEXT_PHASE=phase-production-build or RADAR_SKIP_DATABASE=1, and Notion direct read is off src/data/merged-content.json. No database access at build time — this is why npm run build sets RADAR_SKIP_DATABASE=1.
Cloudflare content store RADAR_CONTENT_STORE=cloudflare or RADAR_NOTION_DIRECT_READ_ENABLED=true A JSON object in R2 at content/radarsite-content-v1.json. The durable public read model; served directly once it exists.
Direct Notion read RADAR_NOTION_DIRECT_READ_ENABLED=true plus NOTION_API_KEY and RADAR_NOTION_DATA_SOURCE_ID Bootstrap fallback when the snapshot has not been written yet.
Postgres DATABASE_URL is set A single row in studio_content (id = 1) holding the whole content document.
Snapshot fallback Any read above throws and fallbackToSnapshot is set Keeps the public site serving rather than returning an error.

Caching. readPublicContent() wraps the read in unstable_cache under the tag radarsite-public-content-v3, with a revalidate window of 3600 seconds — or 240 when Notion direct read is enabled. A cache failure is treated as an optimisation miss, never as a reason to fail the request.

Publication filter. readPublishedContent() drops any record whose status is draft or archived. Public routes should call this, not readContent(), or unpublished work can leak into a page.

Why a build passing proves little

A production build reads the committed snapshot and never touches the database. A green build therefore says nothing about production data access, the content store, or whether a live route resolves. Database behaviour is checked by the contract-test scripts, not by npm run build.

(04)

Media and storage

src/lib/storage/

Storage sits behind an adapter factory. Callers ask for the storage adapter and never branch on the provider; STORAGE_PROVIDER decides which one is built. R2 is the default, so an environment with the variable unset behaves exactly as it did before the adapter existed.

Storage adapters
Provider Selected when Transport
Cloudflare R2 STORAGE_PROVIDER unset or r2 Native RADARSITE_MEDIA binding inside the Worker; S3-compatible API everywhere else.
Storj STORAGE_PROVIDER=storj S3-compatible gateway.

Delivery. R2_PUBLIC_BASE_URL is the public origin for stored media. It is read in two places that must agree: next.config.ts derives images.remotePatterns from it, and the same value is added to the CSP img-src directive. Change one without the other and images either fail to optimise or are blocked by the policy.

Processing. Uploads are normalised to WebP with sharp before they are stored. The migration and health tooling lives in scripts/ and is covered by its own contract tests.

(05)

The Studio write path

/admin · /api/studio

Reading and writing are deliberately separate. The public site only ever reads; every mutation goes through the Studio at /admin and the /api/studio/* handlers behind it.

Access is gated by STUDIO_ADMIN_PASSWORD. A successful sign-in sets the radar_studio_session cookie, which the Studio routes check before performing any write. There is no public sign-up and no user table — this is a single-operator surface, not a multi-tenant admin.

  • /api/studio Read and write the content document.
  • /api/studio/session Establish and clear the Studio session cookie.
  • /api/studio/tracks Track-story records attached to editorial content.
  • /api/studio/migrate Media migration runs, with a dry-run counterpart.
  • /api/studio/media-health Report on stored media and its relationships.
  • /api/integrations/notion/publish Publish a Notion page into the content store.
Consequential operations

Migration, reconciliation and publish endpoints change durable state. Treat them the way the working principles treat a deployment: plan first, run against a known target, and record what actually happened.

(06)

Cross-cutting concerns

Every route

These apply to the whole application rather than to one feature, which is why they are easy to break from a distance.

Headers set in next.config.ts
Header Value / intent
Content-Security-Policy default-src 'self', object-src 'none', frame-ancestors 'self'. Script sources come from buildScriptSrcDirective() in src/lib/csp.ts.
Strict-Transport-Security max-age=31536000; includeSubDomains
X-Content-Type-Options nosniff
Referrer-Policy strict-origin-when-cross-origin
X-Frame-Options SAMEORIGIN
Permissions-Policy Camera, microphone, geolocation, payment and compute-pressure disabled.
Cross-Origin-Opener-Policy / Resource-Policy same-origin for both.

Request security. src/lib/request-security.ts provides a fixed-window rate limiter and resolves the client address. Forwarded headers are treated as attacker-controlled unless RADAR_TRUSTED_PROXY_HOPS declares how many proxies the deployment owns; the chain is walked from the edge inward rather than trusting the first X-Forwarded-For value.

Monitoring. Sentry is initialised for the server, edge and client runtimes from sentry.server.config.ts, sentry.edge.config.ts and instrumentation.ts. PostHog is initialised in instrumentation-client.ts and stays silent when its project token or host is missing.

Discovery. src/app/sitemap.xml, robots.ts and src/lib/seo.ts build canonical URLs from NEXT_PUBLIC_SITE_URL, falling back to https://radarcharts.net. Preview hosts are rejected so a staging deployment cannot publish itself as canonical.

(07)

Component architecture

src/components/

Components are grouped by the surface they serve, not by type. A marketing component is never imported by a platform route, and the primitives in ui/ carry no product styling of their own.

57 files

marketing/

The public site: hero, pillars, editorial tree, case-study entries, header, footer, players and the editorial body renderer.

11 files

ui/

Structural primitives — button, card, dialog, input, select, sheet, separator. Styling is applied by the consumer; no default skin ships.

9 files

motion/

Client-side motion: smooth scroll, cursor, marquee, parallax, fade and slide-up primitives. All respect prefers-reduced-motion.

10 files

admin/

The Studio panels: editorial studio, CMS panel, migration controls, release links, track stories, share-preview tester.

5 files

platform/

The signed-in app shell, brief form, project card, status badge and admin panel.

10 files

case-study/

Long-form case-study sections: hero, brief, approach steps, gallery, results, credits, next-case teaser.

4 files

three/

WebGL surfaces — hero scene, halftone field, Spline embed — behind a SceneGate so they never block first paint.

49 files

src/lib/

The non-visual core: content, database, storage, media, SEO, security, taxonomy and the Notion and Cloudflare integrations.

Boundaries of this page

What is not here

This page explains structure. It deliberately does not cover the following, because each needs its own verified page rather than a summary here.

  • Environment setup and the full variable list — see the Development Guide.
  • Editorial workflow, taxonomy and Notion publishing — see Content and CMS.
  • Hosting, DNS, Worker deployment and rollback — see Infrastructure and Deployment.
  • Test suites, accessibility and incident response — see Security and Operations.
  • Why a particular choice was made — see Technical Decisions.
Before you change the architecture

Read the file you intend to change, and the tests that cover it. The content fallback chain and the storage adapter are both load-bearing: a change that looks local can alter what every route serves.
